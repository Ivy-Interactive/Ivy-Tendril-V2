## At a glance

Ten locales, the same ones as the docs site and Ivy-Web. English is the source language and every
other locale falls back to it, key by key.

| Code | `hreflang` | Native name        | Plural forms a catalog needs  |
| ---- | ---------- | ------------------ | ----------------------------- |
| `en` | `en`       | English            | `one`, `other`                |
| `de` | `de`       | Deutsch            | `one`, `other`                |
| `ja` | `ja`       | 日本語             | `other`                       |
| `es` | `es`       | Español            | `one`, `many`, `other`        |
| `fr` | `fr`       | Français           | `one`, `many`, `other`        |
| `pt` | `pt-BR`    | Português (Brasil) | `one`, `many`, `other`        |
| `zh` | `zh-CN`    | 简体中文           | `other`                       |
| `ru` | `ru`       | Русский            | `one`, `few`, `many`, `other` |
| `sv` | `sv`       | Svenska            | `one`, `other`                |
| `hi` | `hi`       | हिन्दी             | `one`, `other`                |

- The table lives in `@ivy-interactive/components/i18n` (`SITE_LOCALES`, `LOCALES`, `matchLocale`);
  the docs site re-exports it.
- One small runtime, in the components package, serves both the components' own strings and the
  app's. It is not i18next, but it reads and writes **i18next's JSON format exactly**, so the
  catalogs work with i18next tooling (i18n-ally, translation platforms).
- Keys are checked at compile time against the English catalogs: a typo fails `tsc`.
- In tests a missing key, a missing `{{variable}}`, an unknown format, an unmapped `<tag>` and a
  `<Trans>` tag that pairs with nothing all **throw**, so they fail the test that renders them.

## How it works

**One store.** `src/packages/components/src/i18n/runtime.ts` holds every catalog, the current
language and its subscribers. The components package and the app both translate through it, so one
`changeLanguage` switches every string on screen. There is no provider: hooks subscribe to the store
with `useSyncExternalStore`, which is why a component renders English with no setup anywhere - the
docs site, a unit test, Storybook.

**Typed bindings.** `createTranslation<Resources>()` returns `{ i18n, useTranslation, Trans }`
typed against a set of namespaces:

- app: `src/apps/tendril-app/src/i18n/index.ts`, typed by all of the app's catalogs;
- components: one module per namespace (`src/packages/components/src/i18n/uiDialogs.ts`, …), each
  typed for **its own namespace and `uiCommon`** - the two catalogs importing it registers - and for
  nothing else.

The resources type is the type of the English JSON files, so adding a key to the English file is
what makes it compile. In the components package it is derived in `src/i18n/resources.ts`, in a form
the declaration build can follow: a `t`, a `TFunction` or a key type may appear in any exported
signature there.

**Loading.**

| Catalog                   | English                                                 | Other languages                                        |
| ------------------------- | ------------------------------------------------------- | ------------------------------------------------------ |
| components (`ui*`)        | Bundled statically with the components that use it      | One chunk per language, through an explicit loader map |
| app (`common`, `chat`, …) | Lazy, one chunk per language (`locales/<lng>/index.ts`) | Lazy, the same way                                     |

A component imports its hooks from the module named after its namespace - `@/i18n/uiDialogs` - and
that module registers the namespace's English as it loads. So a component can never render before
its English exists, and the English of a lazily loaded component (the dialogs) stays in that
component's chunk instead of the app's eager bundle. Each namespace module also loads `uiCommon`, the
one namespace every other may reference.

`main.tsx` awaits `initI18n(language)` before the first render. It loads the language's catalogs,
the app's and the components', plus English for the fallback, then renders: no Suspense, no flash
of keys. If a catalog fails to load the app starts in English; if even English fails it still
renders. `i18n.changeLanguage(lng)` loads everything registered for the language first and then
switches; when it is already loaded the switch is synchronous. When two changes overlap, the later
one wins however the loads finish.

**Missing strings.** A key found in neither the current language nor English renders as the key in
production, warns once in development, and throws in both packages' tests.

## File layout

```text
src/packages/components/src/
├── i18n.ts                        # the @ivy-interactive/components/i18n entry (for the app, docs)
└── i18n/
    ├── locales.ts                 # the locale table, findLocale, matchLocale
    ├── runtime.ts                 # store, lookup, plurals, context, interpolation
    ├── intl.ts, format.ts         # Intl formatters (hooks in react.tsx)
    ├── react.tsx, markup.ts       # createTranslation, useTranslation, <Trans>, useLocale, useFormatters
    ├── types.ts                   # key-path types
    ├── catalogCheck.ts            # parity/completeness checks, used by both packages' tests
    ├── namespaces.ts              # the components' namespace list
    ├── register.ts                # the loader map for the non-English catalogs
    ├── resources.ts               # the key types, from the English catalogs
    ├── bindings.ts                # bindNamespace: what the namespace modules are made of
    ├── uiCommon.ts, uiDialogs.ts, uiPlanWorkspace.ts, uiShell.ts, uiVault.ts,
    │   uiJobs.ts, uiReview.ts, uiSettings.ts, uiPanels.ts
    │                              # what components import: everything to translate and format
    └── locales/<lng>/<ns>.json    # + one index.ts per language exporting its namespaces

src/apps/tendril-app/src/
├── i18n/index.ts                  # the app binding, loaders, initI18n  →  import from "../i18n"
├── i18n/enumLabels.ts             # job status / job type / plan state labels
├── state/language.ts              # the language setting (config.yaml `language`)
└── locales/<lng>/<ns>.json        # + one index.ts per language that loads the directory as a chunk
```

Every namespace file exists for every locale, as `{}` until it is translated. A translator fills a
file in; nothing else needs registering.

a key of your own. `settings.json`'s `appearance.language` subtree belongs to the language picker.

## Adding a string

1. Add the English string to `locales/en/<namespace>.json`, under a nested camelCase key.
2. Use it:

   ```tsx
   // app - relative import of the app binding
   import { useTranslation } from "../i18n";

   export function Composer() {
     const { t } = useTranslation("chat");
     return <textarea placeholder={t("composer.placeholder")} aria-label={t("composer.label")} />;
   }
   ```

   ```tsx
   // components - everything from the module named after your namespace
   import { useTranslation } from "@/i18n/uiDialogs";

   export function CreatePrDialog() {
     const { t } = useTranslation("uiDialogs");
     return <DialogTitle>{t("createPr.title")}</DialogTitle>;
   }
   ```

   Another namespace's key is reached with its namespace: `t("common:actions.cancel")`. In the
   components package that is only ever `uiCommon:` - `tsc` rejects any other namespace, because only
   `uiCommon` is guaranteed to be registered wherever your component renders.

3. Add the key to every other locale as well, translated ([Translating](#translating)). CI runs the
   completeness check, so an English key missing from any locale fails the build.
4. Run the package's `format`, `check` and `test` scripts ([Checks and tests](#checks-and-tests)).

**Inside the components package, never import from `@ivy-interactive/components/*`.** There that
specifier resolves to the package's own built `dist/`, which has a store of its own: its formatters
ignore `changeLanguage`, and its missing keys never reach the test setup's handler. Your namespace
module (`@/i18n/<ns>`) exports everything - `useTranslation`, `Trans`, `i18n`, the `TFunction` type,
`useFormatters`, `useLocale` and the `format*` helpers - and a test fails on any self-import.

## Key naming

- **Nested, camelCase, by component or area, then by role**: `composer.placeholder`,
  `jobsTable.columns.status`, `deletePlan.confirm.title`. Roles that recur: `title`, `description`,
  `hint`, `label`, `placeholder`, `ariaLabel`, `tooltip`, `empty`, `error`, `success`, `confirm`.
- A key names **where a string is and what it is for**, not what it says: `emptyState.title`, not
  `noPlansYet`. The English will change; the key should not have to.
- **One key per place.** Two buttons that both say "Delete" in English are two keys unless they are
  the same action - languages that inflect will need different words.
- **No underscores** except the plural and context suffixes below. Never name a context after a
  plural category (`_one`, `_other`, `_many`, …).
- Keys are English-only identifiers; values are the text.

## Interpolation and formats

`{{name}}` inserts a variable, as `String(value)` and nothing more:

```json
{ "planTitle": "Plan {{id}}: {{title}}", "owner": "Owned by {{user.name}}" }
```

```ts
t("planTitle", { id: plan.id, title: plan.title });
t("owner", { user });
```

A plain `{{n}}` is **never** localized, so the English output of an extracted template literal stays
exactly what it was. To localize a number, date or list, ask for a format:

| Placeholder                               | Renders (en)            | Notes                                    |
| ----------------------------------------- | ----------------------- | ---------------------------------------- |
| `{{n, number}}`                           | `1,234.5`               | `de`: `1.234,5`                          |
| `{{n, number(maximumFractionDigits: 1)}}` | `1.2`                   | any `Intl.NumberFormat` option           |
| `{{n, percent}}`                          | `25%`                   | `n` is a fraction: `0.25`                |
| `{{n, currency}}`                         | `$3.50`                 | USD by default; `currency(EUR)`          |
| `{{n, compact}}`                          | `1.2K`, `2.5M`          | each language's own abbreviations        |
| `{{d, date}}`                             | `Sep 22, 2026`          | `Date`, epoch ms or ISO string           |
| `{{d, time}}`                             | `3:04 PM`               |                                          |
| `{{d, datetime}}`                         | `Sep 22, 2026, 3:04 PM` | `date(month: long)` etc. for other parts |
| `{{items, list}}`                         | `a, b, and c`           | `de`: `a, b und c`                       |

Options follow i18next's syntax: `format(key: value; key2: value2)`. The runtime formats in the
current language's `hreflang`.

A variable passed as `undefined` or `null` renders as nothing. A variable **not passed at all** is a
bug, and throws in tests. Values are never HTML-escaped (React escapes what it renders).

Never build a sentence from pieces: `t("a") + name + t("b")` cannot be reordered by a translator.
One key per sentence, with variables.

## Plurals

English writes `_one` and `_other`, and the call passes `count`:

```json
{ "jobCount_one": "{{count}} job", "jobCount_other": "{{count}} jobs" }
```

```ts
// before: `${count} job${count === 1 ? "" : "s"}`
t("jobCount", { count });
```

- Never hand-roll an English plural (`=== 1 ? "" : "s"`, `"item(s)"`). Every such ternary becomes a
  plural key.
- `count` must be a number. It is also a variable: `{{count}}`.
- `_zero` is optional, for a count of exactly 0: `"jobCount_zero": "No jobs"`.
- Each language supplies the forms its rules need (the table [above](#at-a-glance)): Russian writes
  `_one`, `_few`, `_many` and `_other`; Japanese and Chinese only `_other`. The parity test enforces
  it once any form of a key is translated. A missing form falls back to that language's `_other`,
  then to English.
- A form may drop `{{count}}` ("One job") or keep it - but Russian's `_one` also covers 21, 31, …,
  so translations there keep it.
- Forms of one key may use different variables ("Delete {{name}}?" / "Delete {{count}} items?").
  Each translated form is compared with the English form of the same category; a category English
  does not have (`_few`, `_many`) with English's `_other`. Japanese and Chinese then have only the
  `_other` form to say it with, so prefer forms that share their variables.
- The key in code is the base (`jobCount`); the type checker knows it from its suffixed forms.

## Context

A variant chosen by a string instead of a number:

```json
{ "assigned": "Assigned", "assigned_agent": "Assigned to an agent" }
```

```ts
t("assigned", { context: target.kind }); // "agent" → assigned_agent; anything else → assigned
```

Context and plurals combine as `key_<context>_<form>`.

## Markup: `<Trans>`

A sentence with a link or emphasis in it stays **one** string, with named tags:

```json
{ "empty": "No plans yet. <link>Create one</link> or press <kbd>{{shortcut}}</kbd>." }
```

```tsx
// app
import { Trans } from "../i18n";

<Trans
  ns="plans"
  i18nKey="empty"
  values={{ shortcut: "Ctrl+N" }}
  components={{
    link: <button type="button" className="underline" onClick={openNewPlan} />,
    kbd: <TuiKbd />,
  }}
/>;
```

```tsx
// components
import { Trans } from "@/i18n/uiDialogs";

<Trans
  ns="uiDialogs"
  i18nKey="deleteProject.body"
  values={{ name }}
  components={{ strong: <strong /> }}
/>;
```

- Each tag names an entry in `components`; that element is cloned with the translated text as its
  children, so its props (`href`, `onClick`, `className`) survive.
- `<br/>`, `<strong>`, `<i>` and `<p>` render as themselves without an entry. Any other tag needs one,
  or it is reported (and throws in tests).
- Tags have no attributes. Numbered tags (`<0>`) are not supported.
- `{{variables}}` work inside and around tags. A variable's value is never parsed as markup.
- **Text that only looks like a tag goes in a variable.** `recover/<name> <hash>` or
  `<TENDRIL_HOME>/Projects/` inside a `<Trans>` string would pair with nothing and knock out the real
  tags around it; such a tag is reported (and throws in tests). Write
  `"Run <code>{{command}}</code> to restore."` with `values={{ command: "git branch recover/<name> <hash>" }}`.
  In a plain `t()` string angle brackets are just text.
- `count` and `context` are props, as on `t`.
- Do not split a sentence into fragments around an element; that is what `<Trans>` is for.

## Enum labels

Job statuses, job types and plan states are rendered in many places. Their labels live once, in
`common.json` under `enums`, keyed by the value with its first letter lower-cased:

```tsx
import { useEnumLabels, jobStatusLabel } from "../i18n/enumLabels";

const labels = useEnumLabels();
<Badge>{labels.planState(plan.state)}</Badge>; // "Icebox"
<Badge>{labels.jobType(job.type)}</Badge>; // "ExecutePlan"

// outside React, at call time
notify(jobStatusLabel(job.status));
```

- The English label **is** the raw value, which is what the UI showed before - English output is
  unchanged.
- A value the daemon added after this build is shown as it is, never as a key.
- Only the text changes. Logic keeps comparing raw values: `job.status === "Running"`.
- Other enums (verification status, cost kinds, …) belong in the namespace of the code that shows
  them.

## Numbers, dates and relative time

Replace every hard-coded `"en-US"`, every `toLocaleString()` / `toLocaleDateString()` without a
locale (those follow the operating system, not the language the user picked), and every hand-built
`$${x.toFixed(2)}` or "N minutes ago" with the formatters. They format in the current language's
`hreflang` and cache their `Intl` objects.

```tsx
// app: import { useFormatters } from "@ivy-interactive/components/i18n";
// components: import { useFormatters } from "@/i18n/<your namespace>";

const format = useFormatters(); // re-renders on a language change
format.number(tokens); //                            "24,000"
format.currency(cost); //                            "$0.12" (USD)
format.percent(0.873, { maximumFractionDigits: 1 }); // "87.3%"
format.compact(2_500_000); //                        "2.5M"
format.date(plan.created); //                        "Sep 22, 2026"
format.date(day, { month: "short", day: "numeric" }); // "Sep 22"
format.time(job.startedAt); //                       "3:04 PM"
format.dateTime(job.completedAt);
format.list(names); //                               "a, b, and c"
format.relativeTime(pr.updatedAt, { style: "narrow" }); // "3h ago"
```

Outside React use `formatNumber`, `formatCurrency`, `formatPercent`, `formatCompact`, `formatDate`,
`formatTime`, `formatDateTime`, `formatRelativeTime` and `formatList` - from
`@ivy-interactive/components/i18n` in the app, from your namespace's module in the components
package. They read the language at call time.

**Relative time** picks the best unit from seconds to years and counts **whole** units (59 minutes
is "59 minutes ago", 119 is "1 hour ago"). `style: "narrow"` gives the "5m ago" / "3h ago" / "2d ago"
shape the hand-rolled helpers produced - in languages whose narrow form is a phrase. French, Russian
and Swedish write narrow times as a bare signed number ("-3 h"), so there `narrow` renders as `short`
("il y a 3 h") by itself; pass `narrow` without special-casing. `maxUnit: "day"` keeps "45d ago"
instead of "1mo ago"; `numeric: "always"` avoids "yesterday"/"now" (and says "0 minutes ago" for a
span under a minute). For a "just now" below a minute, keep that phrase as a key and use
`selectRelativeTimeUnit(delta)` to decide when to show it.

When converting a format site, choose options that reproduce today's English output. Where no
`Intl` option can (English ordinals such as "21st"), switch to the `Intl` form and update the
affected test assertions in the same change, saying so in the PR - do not keep an English-only
formatting path.

Sorting that depends on language: `a.localeCompare(b, i18n.language)`.

## Code outside React

Stores, controllers and helpers call `i18n.t` **when the string is needed**:

```ts
// app
import { i18n } from "../i18n";

notificationsStore.notifyError(
  i18n.t("jobs:notifications.failed", { type: jobTypeLabel(job.type) }),
);
```

```ts
// components - a pure module such as AgentViewer/status.ts or Vault/gate.ts
import { formatRelativeTime, i18n } from "@/i18n/uiShell";

export function runningSince(startedAt: string): string {
  return i18n.t("uiShell:agentStatus.runningSince", { since: formatRelativeTime(startedAt) });
}
```

- Never translate at module load. A constant evaluated at import is frozen in whatever language the
  app started in. Turn it into a function:

  ```ts
  // before
  export const CHAT_MODE_LABELS: Record<ChatMode, string> = {
    chat: "New chat",
    terminal: "New terminal chat",
  };
  // after
  export const chatModeLabel = (mode: ChatMode): string => i18n.t(`chat:newChat.${mode}`);
  ```

- `i18n.getFixedT(null, "jobs")` returns a `t` bound to a namespace that still translates into the
  language current at each call, so it is safe to create at module level:
  `const t = i18n.getFixedT(null, "jobs");`. (It is i18next's `getFixedT(lng, ns)`: the first
  argument is a language, and `null` means "the current one".)
- A helper that is handed a `t` types it with `TFunction`: `TFunction<"jobs">` from `"../i18n"` in
  the app, plain `TFunction` from your namespace's module in the components package (it is bound to
  that namespace). It may appear in exported signatures.
- A string stored on an object (a toast, a notification) keeps the language it was created in.
  That is acceptable; do not re-translate stored text.
- Keyboard shortcut descriptions: pass `description: t("…")` from the component that calls
  `useShortcut`. It re-registers when the description changes, so the help panel follows the
  language.

## What must not be translated

**The rule of thumb: never translate a literal that code compares, matches with a regex or
`.includes`, parses back, uses as a React key or identity, stores, or sends to the coding agent,
the daemon or GitHub.** English output stays identical and every test runs in English, so breaking
one of these passes every check and fails only for a user who picks another language. Where such a
literal is also shown on screen, split it: a stable id or the raw value for the logic, and a label
looked up from it at render time (the way [enum labels](#enum-labels) work).

- **Literals matched against daemon text.** The daemon speaks English, and these match it:
  `ConfigEditorView.tsx:105` `CONFLICT_MESSAGE` (`.includes`); `OnboardingWizard.tsx:445`
  `/already exists/i`; `utils/systemEvents.ts:22-24` the `FINISHED`/`APPROVED` regexes and the status
  matching below them; `ServiceStatusBanner.tsx:27-33` `badge.includes("Connected" | "Starting" |
"Degraded")`; `InboxView.tsx:1445` `includes("auth login")`; `CodingAgentStep.tsx:11-14,38`
  `checkName` and `EXTRA_MACHINE_CHECK_NAMES` ("GitHub CLI auth" - doctor-check match keys);
  `jobsStore.ts:421` "Stopped by stop-all" (must equal the daemon's message).
- **Markers the app parses back out of text it wrote.** `TendrilQuestions/answers.ts:92-93`
  `SKIPPED_MARKER` / `NO_PREFERENCE_MARKER` and the "Answers:" summary around them;
  `ChatMessageRow.tsx:61` `[Attached Files]:`; `utils/questionMarkdown.ts` `answer:`;
  `PlanRevisionDiff.tsx:31-39` the `plan.md (revision N)` / `diff --git` patch headers; the
  `[Follows up on plan […]]` marker in `PullRequestsView.tsx:410`.
- **Grammar keywords a parser accepts.** `ui/data-table/filter-expression.ts` accepts `AND`, `OR`,
  `contains`, `in`, `is blank`, `equals`, `greater than or equal`, … in English only - translate the
  message around a keyword, never the keyword. The same for `PlanMarkdown/wireframeSource.ts`
  (`name`, `height`, `viewport`, `Desktop`/`Tablet`/`Mobile`), the `[!NOTE]`-style alert markers
  in `lib/markdown-utils.ts`, and the questions YAML fields in `PlanMarkdown/questionsSchema.ts`.
- **Display strings that double as identity.** Split each into an id plus a label:
  `planDetail/actions.ts:172` compares `pendingAction === "Execute Plan"`, the label
  `PlanDetailView.tsx:708,721` passes to `runAction`; `JobCostSheet.tsx:144` keys rows by
  `bucket.kind`; `OnboardingWizard.tsx:17,727` keys the step list by `STEP_TITLES`. The same goes for
  recommendation states (`Accepted`, `Declined`), `ReviewView`'s action ids (`implementRecs`,
  `updatePr`, `complete`), and anything used as a dedupe key.
- **Persisted values.** `NEW_CHAT_TITLE` ("New Chat") is stored as a session title and matched by
  the daemon. Config values, file names and anything else written to disk or sent to the daemon.
- **Protocol and enum values used in logic.** `job.status`, `plan.state`, job types, `chatMode`,
  settings tags, widget event names (`OnSelect`, `OnAction`), icon names, bridge error codes
  (`TUNNEL_PASSWORD_REQUIRED`, `CONFLICT`). Translate only what is displayed.
- **Identifiers.** `data-testid`, ids, class names, storage keys, keyboard key names in shortcut
  definitions, shortcut registry ids, URLs, CLI commands shown as code (`gh auth login`), env var and
  file names inside sentences (`TENDRIL_HOME`, `config.yaml`, `.env`).
- **Text for the coding agent or for GitHub, not the user.** `controllers/updatePrompt.ts`,
  `utils/appComments.ts`, the components' `Dialogs/appComments.ts` and
  `Dialogs/SuggestChangesDialog.tsx:66` `INLINE_ONLY_REQUEST`, the job list `ChatView` serializes into
  a message, `InboxView.tsx:119,201` `buildInboxChatPrompt` / `buildIssueIntake` and the same intake
  in `App.tsx:1043`, `ReviewView.tsx` `buildRecommendationChangeRequest` and its "Line-by-line
  feedback:" block, `RecommendationsView.tsx:290` `[ORIGINAL RECOMMENDATION]…[NOTES]`, and
  `VaultSettingsView.tsx:354-358` `prTitle`/`prBody` ("Opened from the Tendril desktop app."). Only
  their display _labels_ (a button) are UI and are translated.
- **But a draft the user reads and sends as their own words is UI.** The bodies of
  `chat/samplePrompts.ts`, `ConfigEditorView`'s `CONFIG_SAMPLE_PROMPTS` and the drafts
  `PlanDetailView` puts in the composer ("I want to discuss the outcome of this plan…") land in the
  composer for the user to edit and send, so they follow the UI language like any other copy. The
  line is who authors the text: a message the user sends is theirs; text Tendril sends on the user's
  behalf, which the user never sees before it goes, stays English.
- **Daemon and bridge error text.** `describeBridgeError` details, daemon messages
  (`job.statusMessage`, `serviceInfo.statusBadge`) and the HTTP fallbacks' `path`/`status` come from
  the daemon in English. Translate the wrapper around them ("Failed to save: {{error}}"), not the
  detail.
- **Brand and product names**: Tendril, Ivy, GitHub, Claude Code, Codex, MCP, `models.dev`, agent
  and provider labels (`CODING_AGENTS`, `ONBOARDING_AGENTS` - a test holds them equal), and the theme
  preset names in `lib/theme-presets.ts`.
- **User data**: project names, plan titles, level names from `config.yaml`, review action names.
- **Developer-only text**: `console.*` messages, invariant errors thrown by context hooks
  (`useX must be used within …`), `views/debug/DebugView` and `DevTools` (even though their files are
  on the jobs and uiShell lists), story fixtures (`storyModels.ts`, `stories/chart-harness.tsx`).

## Keeping English byte-identical

About 1,900 English text assertions in the app's tests and 228 Storybook image snapshots depend on
the English not changing by a single character.

- Move each string **verbatim**: the same `…` or `...`, `—` or `-`, curly or straight quotes,
  trailing punctuation and spacing.
- **Write characters, not HTML entities.** JSX text escapes (`&apos;`, `&quot;`, `&ldquo;`, `&rdquo;`,
  `&bull;`, `&rarr;`, `&hellip;`, `&nbsp;`) are decoded by JSX, but nothing decodes them in a catalog:
  `"Don&apos;t"` would show `&apos;` on screen. Write `'`, `"`, `“`, `”`, `•`, `→`, `…`, and a real
  U+00A0 for `&nbsp;`. The parity test rejects an entity in any catalog.
- A template literal becomes a key with variables and the same text: `` `Plan ${id} of ${total}` ``
  → `"Plan {{id}} of {{total}}"` with raw values (a plain `{{n}}` is never reformatted).
- JSX text that spans elements (`Press <b>Enter</b>{" "}to send`) becomes one `<Trans>` string with
  the same spacing.
- English plural forms must produce exactly what the old ternary did.
- Run the package's tests. A failing text assertion means the English changed - fix the catalog, not
  the test (formatting sites excepted, see above).

## Checks and tests

**Run every command from the repository root, through `pnpm --filter`.** Never run `pnpm` or
`pnpm exec` with the working directory inside `src/packages/components`: that directory has a
`pnpm-workspace.yaml` of its own, so pnpm treats it as a separate workspace, installs a second copy
of every dependency (React included) into `src/packages/components/node_modules/.pnpm` and rewrites
`src/packages/components/pnpm-lock.yaml`. Everything that imports the components package - the docs
tests first - then fails with two Reacts loaded (`Cannot read properties of null (reading
'useMemo')`). If it happens: restore that lockfile from git, delete
`src/packages/components/node_modules`, and run `pnpm install --frozen-lockfile` from the root.

| What                                      | Command                                                                  |
| ----------------------------------------- | ------------------------------------------------------------------------ |
| Format (oxfmt formats JSON and Markdown)  | `pnpm --filter <package> format`                                         |
| Format + lint + types                     | `pnpm --filter <package> check`                                          |
| Types only                                | `pnpm --filter <package> typecheck`                                      |
| Tests                                     | `pnpm --filter <package> test`                                           |
| One test file                             | `pnpm --filter <package> test -- tests/i18n-catalogs.test.ts`            |
| Rebuild components (the app uses `dist/`) | `pnpm --filter @ivy-interactive/components build`                        |
| Completeness (always on in CI)            | `I18N_REQUIRE_COMPLETE=1 pnpm --filter <package> test i18n-completeness` |

`<package>` is `@ivy-interactive/tendril-app` or `@ivy-interactive/components`. The app consumes
the components package's **built** `dist/`: after changing a component or a components catalog,
rebuild it before running the app's tests (the app's `typecheck`/`build` scripts do this
themselves).

What the tests enforce:

- **Missing keys throw** in both packages' test setups, as do missing variables, unknown formats,
  unmapped `<Trans>` tags and `<Trans>` tags that pair with nothing. The app's setup installs every
  English catalog synchronously, in English.
- **`i18n-catalogs.test.ts`** (both packages) - parity: every locale has every namespace file and
  nothing else; no key English lacks (plural forms count as their base key); no object/string
  mismatch; no empty or non-string values, and no HTML entities; the same `{{variables}}` and
  `<tags>` as English (a plural form: as English's form of the same category, or `_other` for one
  English lacks; `{{count}}` optional; an extra `_zero` may use fewer); every plural form the
  language needs once a key is translated at all, and no form it never uses. English's own plural
  keys need `_one` and `_other`. The namespace registries (`APP_NAMESPACES`,
  `COMPONENT_NAMESPACES`) must match the English files.
- **`i18n-completeness.test.ts`** (both packages) - every English key in every locale. It runs
  only with `I18N_REQUIRE_COMPLETE=1`, which CI sets on its frontend test step: every locale is
  complete, so an English key added without its translations fails CI. Set it locally to see what
  is missing.
- **Key types** - `tsc` fails on an unknown key or namespace, and in the components package on a
  namespace your module does not register (`tests/i18n-app.test.tsx`, `tests/i18n-types.test.tsx`
  pin this down).
- **`i18n-namespaces.test.ts`** (components) - what each namespace module exports, and that nothing
  in `src/` imports `@ivy-interactive/components/*`.

## Translating

- Fill in `locales/<lng>/<namespace>.json` for your language, mirroring English's keys. Leave out
  what you have not translated: it renders in English.
- Keep every `{{variable}}` and every `<tag>` exactly as English has them; translate the text
  around and inside tags. Do not translate variable or tag names.
- Supply every plural form your language needs (the table [above](#at-a-glance)). `_zero` is
  optional.
- Keep brand names, product names and code in English.
- Plain, UI-register language; match the tone of the English.
- Plain text only: write characters, never HTML entities.
- Run `pnpm --filter <package> format` and the tests; the parity test reports anything malformed.

## The language setting

- `config.yaml`'s top-level `language`: a locale code, or `system` (or nothing) to follow the
  operating system. The daemon does not model the key - it round-trips through `TendrilSettings`'
  catch-all - so `tendril config set language de` works from the CLI.
- Settings → Appearance → Language offers "System default" and each language by its own name. It
  applies on the change, then writes `language` through `putConfig`; a failed write switches back to
  what `config.yaml` holds, and a language whose catalogs will not load is neither applied nor
  written. Choices can overlap (arrow keys on the select fire one per option): one overtaken while
  its catalogs load is neither written nor toasted, and a config change event that arrives while a
  choice is being applied or saved waits until it has been.
- `state/language.ts` resolves the setting (`system` → `matchLocale(navigator.languages)`: an exact
  code or `hreflang` first, then the base language; every `zh-*` is `zh`, every `pt-*` is `pt`,
  anything else is English), applies it (`i18n.changeLanguage`, `<html lang dir>`), and mirrors an
  applied preference to `localStorage["tendril-language"]` so the next start paints in the right
  language before `config.yaml` has been read. The mirror is written only when a preference is
  applied, never at start-up.
- `App` calls `initLanguage()` on mount, a config change event calls `refreshLanguage()` (so a CLI or
  raw-editor edit applies live), and so does every (re)connection to the daemon - the mount-time read
  fails when the daemon starts after the webview.
- Known gap: macOS WKWebView can report `navigator.language` as `en-US` whatever the OS language, so
  "System default" may resolve to English in the packaged app. Choosing a language explicitly always
  works.

## Storybook

The components Storybook has a **Locale** toolbar global (default English). It switches the shared
store, so every story renders its strings in that language; `<html lang>` follows. English visual
baselines keep their names; a run in another language writes baselines with a `-<lng>` suffix.

## Bundle budget

`tests/code-splitting.test.tsx` caps the app's eager JavaScript at 1.6 MiB. The runtime and the
components' English catalogs are eager; the app's catalogs and every non-English components catalog
are lazy chunks. Keep it that way: never import a catalog JSON statically from app code, and never
add a static import of a non-English locale module.

## Moving to i18next later

The catalogs are already i18next JSON v4, so a swap changes code, not data:

- `createTranslation<R>()` → i18next's `CustomTypeOptions` with the same resources type; `useTranslation`,
  `<Trans>` (named tags via `components`), `i18n.t`, `i18n.changeLanguage`, `i18n.language` and
  `i18n.getFixedT(lng, ns)` keep their call sites.
- Register formatters for the names i18next does not build in: `percent`, `compact`, `date`, `time`,
  and a `currency` that defaults to USD.
- Differences to reconcile: this runtime falls back from a missing plural category to the same
  language's `_other` (i18next falls back to the next language), renders a missing variable as
  nothing (i18next keeps `{{name}}`), and decodes no HTML entities (react-i18next's `<Trans>`
  unescapes a few, which is moot once the catalogs hold none).
