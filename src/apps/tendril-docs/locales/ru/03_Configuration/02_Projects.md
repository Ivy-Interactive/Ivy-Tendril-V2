# Настройка проектов

Tendril поддерживает одновременное управление несколькими проектами. Каждый проект определяет собственные репозитории [Git](https://git-scm.com), этапы верификации, выделение портов, переменные окружения, песочницы безопасности и пользовательские навыки.

## Добавление проектов и управление ими

Проекты можно настраивать визуально через **Settings > Projects** или объявлять в `$TENDRIL_HOME/config.yaml` (см. [Установка и настройки](01_Setup.md)):

- **Мастер добавления проектов (Add Project Wizard)** — нажмите **Add Project** в боковой панели Settings, чтобы зарегистрировать проект, указав путь к его репозиторию, начальный цвет и стандартные этапы верификации.
- **Встроенное переименование** — нажмите на значок карандаша рядом с именем проекта в заголовке, чтобы переименовать его. Tendril проверяет имя на уникальность среди других проектов и автоматически обновляет связанные записи планов.
- **Выбор цветовой плашки (Color Swatch Picker)** — выберите акцентный цвет из палитры 32 цветов Ivy (`ColorSwatchField`). Этот цвет отличает проект в [Панели управления](../04_Apps/01_Dashboard.md), очереди [Планов](../04_Apps/03_Plans.md), очереди [Ревью](../04_Apps/02_Review.md) и трекере [Pull Requests](../04_Apps/06_PullRequests.md).
- **Контекст (Context)** — инструкции в формате Markdown, описывающие терминологию предметной области, архитектурные ограничения и стандарты кодирования. Этот контекст добавляется перед инструкциями промптваров для всех запусков агентов в данном проекте.

### Пример `config.yaml`

```yaml
projects:
  - name: Global Engine
    color: Emerald
    context: |
      Основные службы движка, написанные на Rust с CLI на TypeScript.
      Следуйте стандартным дизайн-токенам Ivy и обеспечьте прохождение всех тестов.
    repos:
      - path: ~/repos/global-engine
    verifications:
      - name: Build
        required: true
      - name: Test
        required: true
      - name: Lint
        required: true
      - name: CheckResult
        required: true
    reviewActions:
      - name: Run E2E
        command: pnpm test:e2e
        condition: "${hasChanges}"
    ports:
      backend:
        defaultPort: 8080
        description: API gateway service
    envFiles:
      - path: .env
        template: .env.example
        overrides:
          PORT: "${ports.backend}"
          DATABASE_URL: "sqlite://${env.TENDRIL_HOME}/dev.db"
    wireframes: true
    wireframeGuard: true
    sandboxMode: Off
    securityPreset: Standard
```

## Репозитории и рабочие деревья Git (Git Worktrees)

Проекты Tendril связывают один или несколько репозиториев [Git](https://git-scm.com) (`repos:`).

Когда агент выполняет план через `ExecutePlan`, он изолирует генерацию кода от вашей локальной среды разработки:

- **Выделенные рабочие деревья Git** — Tendril создаёт изолированную ветку рабочего дерева Git (`tendril/<planId>-<slug>`), ответвлённую от вашей целевой ветки. Ваше рабочее дерево, ветка и IDE остаются нетронутыми.
- **Параллельное выполнение** — несколько планов могут выполняться одновременно в разных репозиториях без конфликтов блокировок git.
- **Безопасный откат и удаление** — неудачные или отклонённые запуски можно чисто удалить без ручной очистки git.
- **Очистка рабочих деревьев (Worktree Reaper)** — автоматическая фоновая служба удаляет неиспользуемые или завершённые рабочие деревья в соответствии с параметрами `worktreeReaperInterval` и `worktreeReaperGrace` из [Установки и настроек](01_Setup.md).

## Конвейеры верификации

Проекты определяют упорядоченную последовательность рубежей верификации, которые агенты должны успешно пройти до передачи работы на этап [Ревью](../04_Apps/02_Review.md):

- **Сортируемый порядок** — перетаскивайте шаги верификации в нужную последовательность выполнения (`SortableVerificationList`).
- **Обязательные этапы** — отмечайте верификации как обязательные. План отображается со статусом `Verified` в [Ревью](../04_Apps/02_Review.md) только в том случае, если все обязательные проверки завершились успешно.
- **Пользовательские верификации** — добавляйте специфичные для проекта команды и промпты верификации (например, `cargo clippy`, `pnpm check`, `pytest`). Для управления через терминал см. [Верификация через CLI](../09_Advanced/01_CLI/03_Verification.md).

## Действия при ревью (Review Actions)

Настраивайте кнопки быстрых действий, отображаемые на панели инструментов приложения [Ревью](../04_Apps/02_Review.md) (`reviewActions:`):

- `name` — название действия, отображаемое на кнопке панели инструментов.
- `command` — команда оболочки, выполняемая в рабочем дереве плана.
- `condition` — опциональное условие выполнения (например, `${hasChanges}`).

## Порты и файлы окружения

Сложным проектам часто требуются изолированные порты и конфигурации окружения:

- **Выделение портов (`ports:`)** — объявление именованных портов (например, `backend`, `frontend`). Если порт по умолчанию уже занят, Tendril выделяет свободный порт и предоставляет его через переменные `${ports.<name>}`.
- **Файлы окружения (`envFiles:`)** — автоматическое воссоздание файлов `.env` внутри рабочих деревьев агентов на основе базового шаблона (например, `.env.example`) и построчных переопределений ключей/значений с поддержкой переменных `${ports.<name>}`, `${env.<VAR>}` и `%VAR%`.

## Безопасность агентов и песочница

Tendril предоставляет гибкие средства контроля безопасности на уровне проекта:

- **Предустановки безопасности (Security Presets)** — выберите `Strict`, `Standard`, `Permissive` или `Custom`. Предустановки определяют правила изоляции и доступа к файлам по умолчанию.
- **Режим песочницы (Sandbox Mode)** — выбор изоляции во время выполнения: `Off`, [Docker](https://www.docker.com) или [Bubblewrap](https://github.com/containers/bubblewrap).
- **Доступ к файлам вне репозитория** — управление тем, разрешено ли агентам читать файлы за пределами дерева репозитория (`Deny`, `ReadOnly`, `Full`).
- **Автовыполнение команд в терминале** — выбор режима запуска команд оболочки: выполнять автоматически (`AllowAll`), запрашивать подтверждение (`RequireConfirmation`) или запретить выполнение (`DenyAll`).
- **Разрешения для файлов** — детальные правила для путей: `Allow <path>`, `Ask <path>` или `Deny <path>`.
- **Вайрфреймы и Wireframe Guard** — включите `wireframes` для генерации прототипов интерфейса в планах и `wireframeGuard` для проверки того, что временный код прототипов проверен перед попаданием в продакшен pull request.

## MCP-серверы и навыки проекта

Расширяйте возможности агента для конкретного проекта:

- **Серверы MCP (`mcpServers:`)** — регистрация серверов [Model Context Protocol](https://modelcontextprotocol.io) с областью видимости проекта с пользовательскими исполняемыми файлами, аргументами и переменными окружения. См. [Интеграция с MCP](../09_Advanced/03_MCP.md).
- **Навыки (`skills:`)** — оснащение агентов специфичными для проекта процедурами и инструкциями в markdown. См. [Руководство по навыкам](../06_CodingAgents/00_Skills.md).

## Локальный контекст репозитория

Tendril автоматически находит и добавляет документацию из корня репозитория к контексту промптваров:

- **`CLAUDE.md`** — рекомендации и соглашения для Claude Code. См. [Руководство по Claude Code](../06_CodingAgents/01_ClaudeCode.md).
- **`AGENTS.md` / `DEVELOPER.md`** — командные стандарты разработки, требования к тестированию и соглашения по кодовой базе.

## Опасная зона: Remove vs. Delete

Настройки проекта завершаются двумя действиями в Опасной зоне (Danger Zone):

```
[ Remove Project ]  (Контурная кнопка)
Удаляет проект из config.yaml. Клонированные репозитории, папки планов и история
сохраняются на диске, поэтому повторное добавление проекта по имени восстанавливает его.

[ Delete Project ]  (Деструктивная кнопка)
Безвозвратно удаляет планы проекта, его клонированные репозитории в
<TENDRIL_HOME>/Projects/, строки в базе данных и запись в конфигурации. Это действие
необратимо и требует предварительного ввода точного имени проекта.
```

> [!WARNING]
> **Remove Project** только снимает проект с регистрации в конфигурации, сохраняя файлы на диске. **Delete Project** навсегда удаляет репозитории, планы и записи базы данных, требуя ввода точного названия проекта для подтверждения.
