# Политика классификации данных телеметрии

## Назначение

Этот документ определяет, какие данные Tendril имеет и не имеет права отправлять в сторонние сервисы телеметрии (PostHog). Цель состоит в том, чтобы собирать полезную аналитику, уважая конфиденциальность пользователей.

Политика следует за кодом: она перенесена из `TELEMETRY.md` оригинального приложения Tendril и сокращена до событий, фактически подключённых в V2.

## Согласие (Opt-in), а не отказ (Opt-out)

**Телеметрия отключена по умолчанию, пока вы явно её не включите.** Только явное указание `telemetry: true` в файле `config.yaml` активирует сбор данных; отсутствие ключа и значение `telemetry: false` работают идентично: клиент не создаётся, события не ставятся в очередь, и сетевые вызовы не выполняются. Ключ считывается ровно в одном месте: `TendrilSettings::telemetry_enabled` в [config.rs](../src/crates/tendril-core/src/config.rs), и V2 никогда не добавляет этот ключ самостоятельно: сохранение файла `config.yaml`, в котором он отсутствует, оставляет его отсутствующим, а не проставляет `telemetry: false`. Это сделано для того, чтобы при циклической перезаписи файла, используемого совместно с оригинальным приложением (которое считает отсутствующий ключ включённым), телеметрия того приложения не отключалась. Явное значение сохраняется без изменений.

**Это осознанное расхождение.** Оригинальное приложение работало по принципу opt-out: параметр `Telemetry` по умолчанию был равен `true`, а в его файле `TELEMETRY.md` утверждалось: «Телеметрия работает по принципу opt-out: она включена по умолчанию». В V2 значение по умолчанию — выключено, поскольку включение сбора данных — это не то решение, которое порт должен принимать скрытно от имени пользователя. Расхождение безопасно только в одну сторону: V2 отправляет меньше данных по сравнению с оригиналом, но никогда не отправляет лишнего. Чтобы вернуть прежнее поведение, измените значение поля по умолчанию и реализацию `Default` в [config.rs](../src/crates/tendril-core/src/config.rs) обратно на `Some(true)`.

Пользователи идентифицируются исключительно по случайному UUID, сохраняемому в `<TendrilHome>/.anonymous-id`. Он никогда не формируется на основе имени пользователя, имени компьютера или репозитория. (Оригинальное приложение предпочитает путь `<LocalAppData>/Tendril/.anonymous-id`; поэтому компьютер, на котором запущены оба приложения, считается двумя установками.)

## Правила классификации

### РАЗРЕШЕНО — Агрегированные и неидентифицирующие данные

- **Количественные показатели**: количество проектов, репозиториев, планов, заданий (только общие агрегированные суммы)
- **Длительность**: время выполнения операций в секундах
- **Состояния/Типы**: значения enum, названия состояний, типы заданий (например, `CreatePlan`, `ExecutePlan`)
- **Уровни**: уровни планов (например, `Bug`, `Feature`, `Epic`)
- **Версии**: строки версий приложения, названия и версии операционной системы
- **Провайдеры агентов**: имена кодинг-агентов (например, `claude`, `codex`, `copilot`, `gemini`, `opencode`, `antigravity`, `apple`, `ivy`)
- **Булевы флаги**: флаги функций (feature flags), состояния конфигурации (например, `llm_configured: true`)
- **Дескрипторы технологий**: хэш стека проекта (см. ниже)
- **Односторонние хэши с солью установки** для идентификаторов, которые иначе были бы запрещены (см. ниже)

#### Хэш стека (`stack_hash`)

Хэш дескриптора стека — это каноничная, сохраняющая сходство сигнатура технологического стека проекта, например, `fe.ts:react+next+tailwind/be.rs:axum/db:sqlite/test:vitest`. Он формируется исключительно из фиксированного словаря идентификаторов языков, фреймворков, баз данных и тестовых библиотек — по своей структуре он не содержит имён, путей, версий, счётчиков или произвольного текста. Он указывает, на каких стеках используется Tendril, не раскрывая, чей это проект.

#### Идентификатор плана с солью установки (`plan_uuid`)

Прямые идентификаторы планов остаются запрещёнными, но события по-прежнему должны группироваться по планам.
Функция `telemetry::derive_plan_uuid` генерирует `SHA256("tendril-plan:" + anonymous_id + ":" + plan_id)`, усечённый до 16 байт и отформатированный как UUID v8 согласно RFC 9562, вместо исходного идентификатора:

- анонимный идентификатор служит уникальной солью для каждой установки, поэтому для плана `00042` на каждой установке вычисляется разное значение, что исключает корреляцию между независимыми пользователями
- хэш является односторонним, поэтому последовательный номер никогда не покидает локальную машину
- он привязан к одному анонимному пользователю, благодаря чему группирует события без раскрытия личности

Идентификаторы сначала нормализуются до пяти цифр, поэтому числовая форма из базы данных (`42`) и форма имени папки (`00042`) дают одинаковое значение.

Любая будущая необходимость корреляции запрещённого идентификатора должна использовать именно этот шаблон хэширования с солью, но ни в коем случае не исходное значение.

### ЗАПРЕЩЕНО — Идентифицирующая информация

Никогда не отслеживать:

- **URL-адреса**: URL репозиториев, PR или issue
- **Пути**: пути к файлам, пути к папкам, абсолютные пути к репозиториям
- **Имена пользователей**: имена пользователей GitHub, названия организаций, адреса электронной почты
- **Названия репозиториев** и **названия проектов** — даже общие названия раскрывают рабочий контекст
- **Последовательные идентификаторы**: ID планов, номера issue, номера PR (вместо этого хэшируйте их с солью установки — см. `plan_uuid`)
- **Пользовательский ввод**: описания задач, сообщения коммитов, содержимое планов
- **Заголовки**: заголовки планов, тем issue, темы коммитов
- **Вывод агентов**: транскрипты, вызовы инструментов или сообщения об ошибках, которые могут содержать пользовательские данные

## Принципы принятия решений

1. Может ли это поле идентифицировать человека или организацию? → Запрещено
2. Может ли оно раскрыть конфиденциальную информацию о репозитории? → Запрещено
3. Может ли оно раскрыть, над чем именно работает пользователь? → Запрещено
4. Можно ли сопоставить его между пользователями для их деанонимизации? → Запрещено, если только оно не приправлено солью анонимного ID и не захэшировано в одну сторону
5. Даёт ли оно полезную агрегированную аналитику? → Разрешено

**Если сомневаетесь — не включайте.**

## Добавляется к каждому событию

Супер-свойства (super properties), устанавливаемые один раз за процесс в [client.rs](../src/crates/tendril-core/src/telemetry/client.rs):

| Свойство | Статус | Примечания |
|---|---|---|
| `$session_id` | Соответствует | Случайный UUID, новый для каждого процесса |
| `$geoip_disable: false` | Принято | PostHog определяет страну по IP-адресу запроса; сам IP не сохраняется как свойство события |
| `app_version` | Соответствует | Версия крейта |
| `os` | Соответствует | Название платформы |
| `os_version` | Соответствует | Выпуск `uname` на Unix, семейство платформ в остальных ОС |

`distinct_id` (анонимный идентификатор) прикрепляется к каждому событию. Свойства `distribution` / `source` из оригинального приложения опущены: они содержат значение .NET `AppBrand`, не имеющее эквивалента в V2.

## Аудит текущих событий

Все события соответствуют этой политике. Контексты представляют собой строго типизированные структуры в [events.rs](../src/crates/tendril-core/src/telemetry/events.rs), поэтому набор свойств определяется на этапе компиляции, а не через произвольный словарь.

| Событие | Свойства | Отправляется из |
|---|---|---|
| `app_started` | `version`, `project_count`, `llm_configured` | `run_server`, после захвата главной блокировки |
| `job_created` | `job_type`, `agent`, `plan_uuid` | `JobManager::start_job_with` |
| `job_completed` | `job_type`, `status`, `duration_seconds`, `agent`, `plan_uuid` | `finish_job` |
| `plan_created` | `level`, `duration_seconds`, `agent`, `stack_hash`, `plan_uuid` | `finish_job`, `CreatePlan` с результатом выполнения |
| `pr_created` | `duration_seconds`, `agent`, `plan_uuid` | `finish_job`, `CreatePr` |
| `plan_state_transition` | `from_state`, `to_state`, `plan_uuid` | `apply_plan_state`, после успешной записи на диск |

`plan_uuid` всегда представляет собой производное значение с солью установки: места вызова передают исходный ID плана в типизированный контекст, а клиент хэширует его перед фиксацией, благодаря чему исходный ID не сможет попасть в PostHog даже из вызывающего кода, не знающего об этом правиле.

### Определены, но не подключены

Для `onboarding_completed` и `project_created` есть структуры контекста в [events.rs](../src/crates/tendril-core/src/telemetry/events.rs), но нет точек вызова: в V2 нет процесса онбординга, а создание проектов происходит в процессе CLI, где клиент не установлен. Они существуют для того, чтобы будущий план добавил точку вызова, а не менял схему.

Клиент функционирует только в процессе демона. Вызов CLI никогда не выполняет `telemetry::install`, поэтому `tendril plan ...` ничего не отправляет.

## Реализация

- [events.rs](../src/crates/tendril-core/src/telemetry/events.rs) — типизированные контексты, обеспечивающие соблюдение политики на этапе компиляции. Новые события описываются структурами, а не динамическими коллекциями свойств.
- [client.rs](../src/crates/tendril-core/src/telemetry/client.rs) — клиент PostHog, анонимный ID, вычисление plan uuid. Каждый метод `track_*` перехватывает собственные ошибки и лишь помещает данные в очередь, которую разгружает фоновая задача: телеметрия ни в коем случае не должна приводить к сбоям или замедлению выполнения заданий.
- [telemetry_test.rs](../src/crates/tendril-core/tests/telemetry_test.rs) — проверяет полное отсутствие сетевых вызовов в отключённом состоянии, точный набор свойств каждого подключённого события и алгоритм вычисления plan uuid.
