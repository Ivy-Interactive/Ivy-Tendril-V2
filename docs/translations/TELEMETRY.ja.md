# テレメトリデータ分類ポリシー

## 目的

本文書は、Tendril がサードパーティのテレメトリサービス（PostHog）に送信できるデータと送信できないデータを定義します。その目的は、ユーザーのプライバシーを尊重しながら、有用な分析情報を収集することです。

本ポリシーはコードとともに管理されます。元の Tendril アプリの `TELEMETRY.md` から移植され、V2 で実際に接続されているイベントに合わせて調整されています。

## オプトイン方式（オプトアウトではない）

**明示的に有効にしない限り、テレメトリはオフです。** `config.yaml` 内で明示的に `telemetry: true` と設定されている場合のみ有効化されます。キーが存在しない場合および `telemetry: false` はまったく同じように動作します。クライアントは構築されず、イベントはキューイングされず、ネットワーク呼び出しも一切試行されません。このキーは [config.rs](../../src/crates/tendril-core/src/config.rs) の `TendrilSettings::telemetry_enabled` という 1 箇所でのみ読み取られます。また、V2 が自動的にこのキーを*挿入*することはありません。キーが存在しない `config.yaml` を保存しても `telemetry: false` を書き込むのではなく未設定のまま保持するため、キーが存在しないことを「オン」と解釈する元のアプリと共有されたファイルを行き来しても、そのアプリのテレメトリをオフにしてしまうことはありません。明示的な値はそのまま保持されます。

**これは意図的な相違点です。** 元のアプリはオプトアウト方式であり、デフォルトで `Telemetry` を `true` に設定し、その `TELEMETRY.md` には「テレメトリはオプトアウト方式です。デフォルトでオンになっています」と記載されていました。V2 がデフォルトでオフにしているのは、データの収集を有効にすることは、移植版がユーザーに無断で決定すべきことではないためです。この仕様の違いは安全な方向（元のアプリと比較して過小に報告することはあっても、過剰に報告することはない）にのみ働きます。これを元に戻すには、[config.rs](../../src/crates/tendril-core/src/config.rs) のフィールドのデフォルト値と `Default` 実装を `Some(true)` に戻してください。

ユーザーは、`<TendrilHome>/.anonymous-id` に永続化されたランダムな UUID のみによって識別されます。ユーザー名、マシン名、リポジトリ名から生成されることは決してありません。（元のアプリでは `<LocalAppData>/Tendril/.anonymous-id` を優先するため、両方のアプリを実行しているマシンは 2 つのインストールとしてカウントされます。）

## 分類ルール

### 許可（ALLOWED） — 集計データおよび個人を特定しないデータ

- **カウント数**: プロジェクト数、リポジトリ数、計画（plan）数、ジョブ数（集計合計のみ）
- **所要時間**: 操作完了にかかった時間（秒単位）
- **状態/種別**: enum 値、状態名、ジョブ種別（例: `CreatePlan`, `ExecutePlan`）
- **レベル**: 計画レベル（例: `Bug`, `Feature`, `Epic`）
- **バージョン**: アプリケーションバージョン文字列、OS 名およびバージョン文字列
- **エージェントプロバイダー**: コーディングエージェント名（例: `claude`, `codex`, `copilot`, `gemini`, `opencode`, `antigravity`, `ivy`）
- **ブール値**: 機能フラグ、設定状態（例: `llm_configured: true`）
- **技術記述子**: プロジェクトスタックハッシュ（後述）
- **インストール別ソルト付き一方向ハッシュ**: 本来禁止されている識別子をハッシュ化したもの（後述）

#### スタックハッシュ (`stack_hash`)

スタック記述子ハッシュは、プロジェクトの技術スタックの標準的かつ類似性を保持するシグネチャです（例: `fe.ts:react+next+tailwind/be.rs:axum/db:sqlite/test:vitest`）。言語、フレームワーク、データベース、テストフレームワークのスラッグで構成される閉じた語彙からのみ構築され、その設計上、名前、パス、バージョン、カウント、自由形式テキストを含みません。誰のプロジェクトであるかを明かすことなく、Tendril がどのスタックで使用されているかを示します。

#### インストール別ソルト付き計画識別子 (`plan_uuid`)

生の計画 ID の送信は禁止されていますが、イベントは計画ごとにグループ化できる必要があります。`telemetry::derive_plan_uuid` は、ID 自体の代わりに、RFC 9562 v8 UUID としてフォーマットされた 16 バイトに切り詰められた `SHA256("tendril-plan:" + anonymous_id + ":" + plan_id)` を出力します：

- anonymous_id はインストールごとのソルトであるため、計画 `00042` はインストールごとに異なる値を導出し、無関係なユーザー同士を相関させることはできません。
- ハッシュは一方向であるため、シーケンシャルなカウンターがマシン外に出ることはありません。
- 単一の匿名ユーザーにスコープされているため、個人特定を広げることなくイベントをグループ化できます。

データベースの整数形式（`42`）とフォルダの形式（`00042`）が同じ値を導出するように、ID は最初に 5 桁に正規化されます。

将来、禁止されている識別子を関連付ける必要が生じた場合も、生の値ではなく、常にこのソルト付きハッシュパターンを使用する必要があります。

### 禁止（FORBIDDEN） — 個人を特定できる情報

以下は絶対に収集しません：

- **URL**: リポジトリ、プルリクエスト、issue の URL
- **パス**: ファイルパス、ディレクトリパス、リポジトリへの絶対パス
- **ユーザー名**: GitHub ユーザー名、組織名、メールアドレス
- **リポジトリ名** および **プロジェクト名** — 一般的な名前であっても業務コンテキストが明らかになるため禁止
- **連続 ID**: 計画 ID、issue 番号、PR 番号（代わりにインストールごとにハッシュ化 — `plan_uuid` 参照）
- **ユーザー入力**: タスクの説明、コミットメッセージ、計画の内容
- **タイトル**: 計画のタイトル、issue のタイトル、コミットの件名
- **エージェント出力**: ユーザーコンテンツが埋め込まれている可能性のあるトランスクリプト、ツール呼び出し、エラーメッセージ

## 判断フレームワーク

1. このフィールドは個人や組織を特定できるか？ → 禁止
2. プライベートリポジトリの情報を明らかにするか？ → 禁止
3. ユーザーが何に取り組んでいるかを明らかにするか？ → 禁止
4. ユーザーを特定するために複数ユーザー間で相関付けることができるか？ → anonymous_id でソルトを付与し一方向ハッシュ化されていない限り禁止
5. 有用な集計インサイトを提供するか？ → 許可

**迷ったときは除外する。**

## すべてのイベントに付加される共通プロパティ

[client.rs](../../src/crates/tendril-core/src/telemetry/client.rs) でプロセスごとに 1 回設定されるスーパープロパティ：

| プロパティ | ステータス | 備考 |
|---|---|---|
| `$session_id` | 準拠 | プロセスごとに新規生成されるランダム UUID |
| `$geoip_disable: false` | 許容 | PostHog はリクエスト IP を国に解決します。IP はイベントプロパティとして保存されません |
| `app_version` | 準拠 | クレートバージョン |
| `os` | 準拠 | プラットフォーム名 |
| `os_version` | 準拠 | Unix では `uname` リリース、その他ではプラットフォームファミリ |

`distinct_id`（anonymous_id）はすべてのイベントに付加されます。元のアプリの `distribution` / `source` プロパティは省略されています。これらは V2 に同等のものがない .NET `AppBrand` を含むためです。

## 現在のイベント監査

すべてのイベントはこのポリシーに準拠しています。コンテキストは [events.rs](../../src/crates/tendril-core/src/telemetry/events.rs) で型付けされた構造体であるため、プロパティセットはルーズなマップではなく、コンパイル時に決定されます。

| イベント | プロパティ | 送信元 |
|---|---|---|
| `app_started` | `version`, `project_count`, `llm_configured` | マスターロック取得後の `run_server` |
| `job_created` | `job_type`, `agent`, `plan_uuid` | `JobManager::start_job_with` |
| `job_completed` | `job_type`, `status`, `duration_seconds`, `agent`, `plan_uuid` | `finish_job` |
| `plan_created` | `level`, `duration_seconds`, `agent`, `stack_hash`, `plan_uuid` | `finish_job`、成果物を伴う `CreatePlan` |
| `pr_created` | `duration_seconds`, `agent`, `plan_uuid` | `finish_job`, `CreatePr` |
| `plan_state_transition` | `from_state`, `to_state`, `plan_uuid` | 書き込みがディスクに到達した後の `apply_plan_state` |

`plan_uuid` は常に派生したインストール別ソルト付きの値です。呼び出し元は生の計画 ID を型付きコンテキストに渡し、クライアントがキャプチャ前にハッシュ化するため、ルールを認識していない呼び出し元からでも生の ID が PostHog に届くことはありません。

### 定義されているが接続されていないもの

`onboarding_completed` と `project_created` は [events.rs](../../src/crates/tendril-core/src/telemetry/events.rs) にコンテキスト構造体が存在しますが、呼び出し箇所はありません。V2 にはオンボーディングフローがなく、プロジェクト作成はクライアントがインストールされていない CLI プロセスで行われるためです。これらが存在するのは、将来の計画でスキーマではなく呼び出し箇所を追加できるようにするためです。

クライアントはデーモンプロセスにのみ存在します。CLI 呼び出しが `telemetry::install` を呼び出すことは決してないため、`tendril plan ...` は何も送信しません。

## 実装

- [events.rs](../../src/crates/tendril-core/src/telemetry/events.rs) — コンパイル時にこのポリシーを強制する型付きコンテキスト。新しいイベントはプロパティバッグではなく、ここで構造体を取得します。
- [client.rs](../../src/crates/tendril-core/src/telemetry/client.rs) — PostHog クライアント、anonymous_id、計画 UUID の導出。すべての `track_*` は独自のエラーを吸収し、バックグラウンドタスクが処理するキューにプッシュするだけです。テレメトリがジョブを失敗させたり遅延させたりすることは決してありません。
- [telemetry_test.rs](../../src/crates/tendril-core/tests/telemetry_test.rs) — 無効時のゼロネットワーク呼び出し、接続されたすべてのイベントの正確なプロパティセット、および計画 UUID の導出を検証します。
